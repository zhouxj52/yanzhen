# 验真：开源选型与创新方案

调研日期：2026-10-22。目标：需求驱动的软件验收、缺陷复现与证据交付。

本文是仓库文档和模型卡调研，尚未运行项目、下载权重、测试模型效果或确认本机部署条件。候选创新是本项目的研发假设，不能据此宣称行业首创。GitHub 公共 API 本次返回限流错误，因此不报告未经核验的最新提交日期、活跃度排名或固定版本。落地时应固定 release/commit 和模型 revision。

## 1. 推荐决策

第一阶段采用 JiuwenSwarm 编排 + Qwen3-Coder-30B-A3B-Instruct 候选模型 + Playwright 执行与取证。JiuwenSwarm 的实际模型接入、工具封装和部署方式需做小样验证，本文没有声称已集成成功。

第二阶段根据真实失败案例，评估 Qwen3-VL-8B-Instruct 或 Midscene 的视觉能力。UI-TARS-1.5-7B 留作 GUI 操作对照模型。首版先验证有 DOM 和接口可访问的 Web 系统。

研究中发现：自动浏览页面、按自然语言测试、生成测试代码、修复测试脚本均已有成熟开源实现。项目的贡献应聚焦于需求约束、跨角色验证、证据判定和缺陷复现。

## 2. 可复用的模型权重

### Qwen3-Coder-30B-A3B-Instruct：首选验证候选

- GitHub：https://github.com/QwenLM/Qwen3-Coder
- 指定权重和许可：https://huggingface.co/Qwen/Qwen3-Coder-30B-A3B-Instruct （模型卡标明 Apache-2.0）。
- 本项目拟用：需求结构化、验收用例和 Playwright 测试代码生成、日志与源码分析。适用性需要实测，不从官方代码能力直接推导验收准确率。
- A3B 是激活参数规模，不能按只有 3B 总权重来估算显存。量化、上下文、并发和推理引擎会影响资源要求；硬件未知时不承诺本地运行。
- 仓库也列出 Coder-Next 等其他型号；选择 30B 作为起点是控制验证范围，不是断言它是最新或效果最强。

### Qwen3-VL-8B-Instruct：视觉补充候选

- GitHub：https://github.com/QwenLM/Qwen3-VL
- 指定权重和许可：https://huggingface.co/Qwen/Qwen3-VL-8B-Instruct （Apache-2.0）。
- 本项目拟用：检查截图中的弹窗、提示、遮挡和可见状态，辅助定位 DOM 信息不充分的页面。
- 视觉模型判断需要与接口、页面状态或可读取的数据交叉检查。看到“保存成功”不能单独证明数据保存成功。

### UI-TARS-1.5-7B：GUI 操作对照候选

- GitHub：https://github.com/bytedance/UI-TARS
- 指定权重和许可：https://huggingface.co/ByteDance-Seed/UI-TARS-1.5-7B （Apache-2.0）。
- 本项目拟用：后续比较视觉操作路线的稳定性与成本。
- 仓库披露多个研究版本；本次确认公开权重的是这个具体 7B 型号。不可把其他版本或更大模型的展示成绩当成本型号的表现。

## 3. 可复用的工程组件与同类项目

| 项目 | 已有能力及许可 | 本项目处理方式 |
| --- | --- | --- |
| [Playwright](https://github.com/microsoft/playwright) | 浏览器测试和 trace；[Apache-2.0](https://github.com/microsoft/playwright/blob/main/LICENSE) | 作为执行、回放和取证基础；角色会话、测试数据和证据关联由我们实现 |
| [Playwright MCP](https://github.com/microsoft/playwright-mcp) | 基于可访问性快照的浏览器工具接口；Apache-2.0 | 候选 Agent 工具入口；不强制所有固定测试都经模型调用，回归脚本可直接执行 |
| [Midscene](https://github.com/web-infra-dev/midscene) | 自然语言视觉操作、断言、测试报告；MIT | 视觉场景备选，也应作为同类对照；不把自然语言操作和截图报告作为原创点 |
| [browser-use](https://github.com/browser-use/browser-use) | Python 浏览器 Agent；MIT | 通用浏览器 Agent 对照，必要时借用执行适配；不再叠加一个主编排框架。开源库与收费模型、云浏览器需区分 |
| [OpenHands Software Agent SDK](https://github.com/OpenHands/software-agent-sdk) | 代码 Agent SDK 和工作空间能力；MIT | 二期代码修复参考；首版不引入完整修复体系。许可结论仅针对这个 SDK 仓库 |
| [TestZeus Hercules](https://github.com/test-zeus-ai/testzeus-hercules) | 从 Gherkin 步骤执行测试；仓库标明 AGPL-3.0 | 同类方案调研与独立对照；当前不选作直接合入的底座 |

重要同类：[Playwright Test Agents 官方文档](https://github.com/microsoft/playwright/blob/main/docs/src/test-agents-js.md) 已提供 planner、generator、healer。其 healer 会重放并修补失败测试，也可能将认为功能损坏的测试标为 skipped。因此“规划—生成—修复”的编排本身不足以构成本项目的差异。

Playwright 本身已有 [Trace Viewer](https://github.com/microsoft/playwright/blob/main/docs/src/trace-viewer-intro-js.md)，能够查看动作、页面快照和网络等信息。我们的贡献应是把需求、证据和判定关联起来，并构建独立复现过程。

## 4. 自主研发的核心

### 4.1 需求约束与验收契约

把需求转成有来源的结构化契约，至少包括：需求编号、原文位置、角色、资源归属、前置状态、操作、预期结果、禁止结果、证据要求。

示例：普通成员只能查看本人报销单。应生成“本人可见、他人不可见、管理员按约定可见”等相互关联的检查，并在需求不明确时标记待澄清。关键契约经人工审阅或预先标注后冻结；不能从当前产品表现反推其行为必然正确。

### 4.2 跨角色、跨证据检查

为不同角色创建隔离会话，使用受控测试数据核实资源归属。UI 展示、请求响应、再次查询和可选数据库检查共同支持结论。

数据库读取只适用于允许接入的测试环境；无法读取时使用重登、刷新和 API 查询等现有证据，并明确证据范围。权限用例只在本地或授权测试系统执行。

首批关注：角色权限、状态流转、数据持久化。例：页面隐藏他人的报销单，但接口仍返回完整记录；页面提示保存成功，刷新后数据丢失。

### 4.3 保持验收标准的执行修复

分开保存需求契约和执行适配代码。允许在语义等价且有证据时调整定位器、等待和页面操作路径，保留修改前后记录；产品缺陷保持失败状态。

禁止以删除断言、放宽预期、改变角色或跳过测试来宣布验收通过。输出区分：通过、产品不符合要求、执行或环境阻塞、需求不明确。定位器能修复不代表产品功能已修复。

可设计“诱导错误修复”用例来验证这个机制是否减少误判；它是候选研究点，需与现有工具公平比较。

### 4.4 缺陷证据与独立复现

每个问题关联契约编号、环境版本、测试数据准备方式、操作轨迹、必要截图或请求证据和可执行复现脚本。

逐步删减无关动作，并在环境重置后重复运行，检查是否保持同一失败现象。使用实际测试过的“精简复现步骤”表述，未经证明不声称数学意义上的全局最小步骤。

## 5. 在开源权重上继续训练的路径

首版先测未经微调的候选模型，积累经过人工复核的案例。系统创新可以先于权重训练成立，但必须以实验说明贡献。

若主要错误集中在“需求转契约”，可以对代码/语言模型做 LoRA 等轻量适配；若集中在图文证据理解，再评估视觉模型适配。具体训练脚本、显存、数据量和许可在选定 checkpoint 后验证，不先承诺训练可行性。

训练数据候选：需求与契约配对、证据与判定配对、正确定位器修复与错误放宽断言的对比案例。评测真值由人工与独立的确定性检查建立，不能让同一个模型生成答案后自行认证。

所有微调效果必须与同一基础模型在未微调状态下比较。优先按整个项目划分训练集和测试集，避免同一流程的近似轨迹泄漏。

## 6. 可验证的实验计划

先在一个报销或审批演示系统跑通；后续扩展至至少三个不同应用，准备产品正常、真实或受控植入缺陷、环境故障、需求含糊等案例。人工植入与真实缺陷分开报告。30—50 个案例可作为起步目标，不能当作已完成数据或足以证明泛化的样本规模。

对照分两层：

1. 组件实验：固定模型、工具权限、任务、测试数据、预算，逐项增加验收契约、跨角色检查、断言保护、复现精简，说明每个模块的作用。
2. 系统实验：与 Playwright Test Agents、Midscene 和通用 browser-use 路线比较；披露框架、提示、版本和执行方式差异。单独统计视觉模型带来的效果和开销。

指标包括：缺陷检出率、误报率、已知缺陷被错误判通过的比例、阻塞与需求不明分类效果、干净环境重放成功率、执行时间和实际 token/推理成本。重复运行并报告波动，不只挑选一次成功的演示。

## 7. 开源复用与原创归属

依赖通过包或清晰适配层使用，记录来源、固定版本、许可和修改范围，按具体 LICENSE/NOTICE 保留所需声明。模型卡许可与代码仓许可分别核对；首次接入后建立依赖清单。

自有模块建议独立组织：contracts、role_checks、verifier、execution_repair、reproducer、evidence、evaluation。浏览器驱动、基础模型、已有截图和 trace 能力归属上游；项目自行实现需求约束、证据判定、断言保护和复现评测。
